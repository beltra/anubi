# Offline bag replay perception validation

Offline LiDAR bag replay is a validation entrypoint (sibling to MPPI benchmarks and safety regressions per ADR 0009) and is permitted to violate the live-run TF ownership contract from ADR 0005 in one narrow way: when the bag has no body odometry input, DLIO publishes `odom -> base_link` directly. EKF cannot run without `/odom_raw` or a body IMU, so there is no fused odometry to own that TF; without an owner, slam_toolbox and the Nav2 costmaps cannot anchor scans, defeating the validation purpose.

The exception is scoped to the offline replay launch entrypoint (`robot_nav/launch/bag_perception.launch.py`) and the wrapper `scripts/replay_bag_perception.sh`. Live runs (real hardware, sim) continue to require body odometry through the EKF and keep the EKF as the single TF owner. The hardware bridge, safety chain, and command chain are not started in replay mode, so the `/cmd_vel_*` arbiter cannot accidentally consume DLIO-derived TFs in a real-robot context. The relevant production invariants in ADR 0003 (safety arbiter command chain) and ADR 0005 are unchanged.

## G1 replay (bags/g1/lidar_record)

The G1 counterpart (`robot_nav/launch/bag_perception_g1.launch.py` + `scripts/replay_bag_perception_g1.sh`) extends the same exception with three G1-specific deviations, all scoped to the replay entrypoints:

1. **DLIO owns `odom -> base_footprint`, not `odom -> base_link`.** DLIO anchors the odom origin at its tracked frame's start pose, and the STVL obstacle heights being tuned are odom-frame z values whose live contract puts the floor at z = 0 (the EKF tracks the floor-level `base_footprint`). Tracking `base_link` (the pelvis) would shift the replay's floor datum by the standing height and silently bias every tuned height. `frames/baselink` is therefore `base_footprint` and the DLIO extrinsics are floor-relative (`dlio_params_g1_bag.yaml`).

2. **The bag's `/tf_static` is dropped from playback** (unlike the Go2 flow, which plays it). The recording's Unitree-side static tree carries an IDENTITY `base_link -> base_footprint` (base_footprint co-located with the pelvis); replaying it would both fight the replay's floor-level `base_footprint -> base_link` static and re-introduce the datum shift from point 1. All statics are regenerated fresh: robot_state_publisher (URDF), a floor-level `base_footprint -> base_link`, an upright `base_footprint -> lidar_stabilized`, and `mid360_link -> livox_frame` (roll = pi, the value the bag's own static tree carried).

3. **Inverted-cloud + measured-mount righting (bag-scoped ONLY).** The recording predates the live driver's MID360_config.json `roll:180` righting, so the bag cloud is inverted (floor above the sensor in `livox_frame`). Additionally, a floor-plane fit over the bag's stationary segment measured the standing sensor attitude 7.2 deg off the nominal URDF mount pitch -- enough to lift floor returns above the STVL `min_obstacle_height` at range and flood the costmap with false floor marks. The bag-scoped DLIO extrinsics and `distortion_corrector_g1_bag.yaml` `sensor_mount_rpy` therefore encode the MEASURED total righting `R_corr * Ry(0.04014) * Rx(pi)` rather than the nominal mount. IMPORTANT: that 7.2 deg is a property of THAT RECORDING's stance, not of the hardware -- the at-rest Livox accel in the later live-stack bag (`bags/g1_planner_tune_20260710_175531`) sits within ~0.7 deg of the nominal mount, and shipping the old-bag calibration to the live `distortion_corrector_g1.yaml` mis-leveled that bag's floor by ~7 deg (tried and reverted the same day). The live config keeps the NOMINAL mount; body attitude belongs to the body-IMU gravity_align path.

Live-stack recordings (`run_g1_real.sh --record-rosbag` bags) replay through a second auto-detected profile: upright `/livox/lidar` cloud, body IMU `/imu/data` driving the real `lidar_level_frame_publisher` + live `distortion_corrector_g1.yaml`, and nominal-mount DLIO extrinsics (`dlio_params_g1_bag_live.yaml`).

Known accepted biases of the legacy-inverted replay: no body IMU means gait roll/pitch is not re-leveled (live gravity_align handles it), and the floor datum carries a ~+0.06 m offset because the fitted standing sensor height (~1.18 m) is below the assumed `standing_height + mid360` chain (1.24 m).
