# Unitree G1

The G1 runs the same autonomy stack as the Go2. What changes is the robot model, the
head-mounted Livox Mid-360, the locomotion bridge, and a few config profiles
(`*_g1*.yaml`).

## Simulation

```bash
scripts/run_g1_sim.sh                          # mapping, ground-truth odometry
scripts/run_g1_sim.sh --use-lio                # DLIO odometry, as on the real robot
scripts/run_g1_sim.sh --locomotion sonic       # test the SONIC Nav2 velocity envelope
```

Gazebo doesn't simulate the walking gait. The G1 is a single rigid body that the
Fortress `VelocityControl` plugin slides around, driven from `/cmd_vel_safe`.
Perception matches hardware: the LiDAR is at the real mount and sees the robot's
own body, and the same self-filter removes those returns.

Known limits:

- With `--use-lio`, DLIO tracks well at rest but drifts while the robot moves, because
  the kinematic base produces unrealistic IMU spikes. The default (ground-truth odometry
  + EKF) is the reliable sim path.
- The Gazebo GUI is slow on software GL and can time out the spawn. Keep the default
  headless mode and use RViz.

## Hardware overview

```
Nav2 -> collision_monitor -> velocity_limiter -> /cmd_vel_safe
     -> cmd_vel_to_amo   (WebSocket :8766) -> amo_driver          (default, same PC)
     -> cmd_vel_to_sonic (ZMQ PUB :5556)   -> g1_deploy_onnx_ref  (--locomotion sonic, Jetson)

DDS rt/lowstate + rt/odommodestate -> g1_state_bridge -> /odom_raw, /imu/data, base_footprint->base_link
Livox Mid-360 -> /livox/lidar, /livox/imu -> robot_lio -> /lidar/points, /lidar/imu -> DLIO + perception
```

- DLIO is on by default (`--no-lio` turns it off), and the EKF fuses it with the body
  odometry.
- `--nav-delay` defaults to 5 s. Keep the robot still during that time so DLIO can
  calibrate.
- **Never run two low-level controllers at once.** That includes `amo_driver`,
  `g1_deploy_onnx_ref` and the stock Unitree sport service. Only one process may write
  `rt/lowcmd`. To switch, stop one, check that it's dead, then start the other.
- Do the first tests on a hoist, with the physical e-stop in your hand and someone
  watching. Treat the software watchdogs as a backstop.

## Robot PC setup

This is the PC that runs Nav2. On top of the normal build (see
[getting_started.md](getting_started.md)), the G1 hardware layer needs:

1. **unitree_sdk2py**:
   `pip install git+https://github.com/unitreerobotics/unitree_sdk2_python.git`.
   The install leaves two problems behind:
   - It doesn't ship `unitree_sdk2py/utils/lib/crc_amd64.so` (or `crc_aarch64.so`), so
     `g1_state_bridge` crashes at startup. Copy `utils/lib/` from the repo into the
     installed package.
   - It upgrades numpy to 2.x, which breaks ROS Humble. Run `pip install "numpy<2"`
     afterwards.
2. **Livox-SDK2**:

   ```bash
   git clone --depth 1 https://github.com/Livox-SDK/Livox-SDK2.git
   cmake -S Livox-SDK2 -B Livox-SDK2/build && cmake --build Livox-SDK2/build -j
   sudo cmake --install Livox-SDK2/build && sudo ldconfig
   ```

   The driver loads the SDK at runtime, so it must be installed on the robot PC, not
   just on the machine you build on.
3. **livox_ros_driver2 package.xml**: it's generated, not checked in. Don't run the
   vendor's `build.sh`, because it wipes `build/` and `install/`. Do this instead:

   ```bash
   cd src/vendors/livox_ros_driver2
   cp -f package_ROS2.xml package.xml && cp -rf launch_ROS2/ launch/
   cd -
   colcon build --symlink-install --packages-up-to g1_bringup \
     --cmake-args -DCMAKE_BUILD_TYPE=RelWithDebInfo -DROS_EDITION=ROS2 -DDISTRO_ROS=humble
   ```

4. **pyzmq** (SONIC only): `sudo apt install python3-zmq`.
5. **CUDA + torch** (AMO only): the AMO policy won't run without a CUDA GPU.

`docker/Dockerfile.real` sets all of this up, but it hasn't been validated yet.

Check the install:

```bash
python3 -c "import unitree_sdk2py"
ldconfig -p | grep -i livox
ros2 pkg executables g1_bringup
```

### Network

- Put the robot PC on the robot's wired LAN with **one** static address,
  `192.168.123.224/24`. This is the Livox host IP in `MID360_config.json`. If the NIC
  picks up a second address (a `169.254.x` or a duplicate), CycloneDDS can bind to the
  wrong one. When that happens, `g1_state_bridge` waits forever for `lowstate` even
  though `ping 192.168.123.161` works. Check with `ip -br addr show <iface>`.
- Pass that wired interface as `--net-if <iface>`, never a wifi one.
- Wifi is fine for SSH. Keep all robot data and commands on the wired LAN. If you lose
  SSH, the robot does **not** stop: cancel the goal locally or use the e-stop.

## Running with AMO (default)

```bash
# terminal 1: the AMO driver (see src/platform/g1_locomotion/README.md)
# terminal 2: sensors + odometry only, no commands yet
scripts/run_g1_real.sh --no-nav --net-if <iface>
```

Check `/odom_raw`, `/imu/data`, `/lidar/points_undistorted`, `/lidar_odom`, `/odom`,
and that the TF tree is complete. Then start the full stack:

```bash
scripts/kill_ros_nodes.sh
scripts/run_g1_real.sh --net-if <iface>
scripts/run_g1_real.sh localization --map <path>.posegraph --net-if <iface>
```

The AMO velocity caps are vx 0.5, vy 0.4 and yaw 0.4 rad/s. Nav2, the bridge and the
driver all enforce them.

## Running with SONIC

SONIC is NVIDIA's whole-body controller
([GR00T-WholeBodyControl](https://github.com/NVlabs/GR00T-WholeBodyControl)). It runs
on a Jetson Orin Nano on the robot. Nav2 stays on the robot PC, because the Jetson
doesn't have enough CPU for both.

### Jetson setup (one time)

Follow the setup guide in the `sonic-g1-locomanipulation` deployment repo. In short:
check out GR00T at `0e35637` and apply that repo's patch. Then install TensorRT 10.7,
download the models, build, and run `sudo scripts/setup_rt_limits.sh`. That repo's
loopback MuJoCo sim lets you test the Jetson side before you go near the robot.

You need one change for this split setup: the bridge binds on the robot PC and the
Jetson connects to it. In `start_deploy_real.sh`, replace `--zmq-host localhost`
with `--zmq-host "${SONIC_ZMQ_HOST:-localhost}"`. The Jetson must be able to reach TCP
port 5556 on the robot PC.

### Start order

1. **Jetson**: start the controller pinned to cores 2-5. Copy
   `scripts/start_sonic_pinned.sh` from this repo to the Jetson and run:

   ```bash
   TMUX=1 SONIC_ZMQ_HOST=192.168.123.224 scripts/start_sonic_pinned.sh
   ```

   Never start SONIC without the pinning. If its DDS threads get starved, it drops
   `LowState` frames, stops writing commands, and the robot falls. Wait for
   `Init Done` and the script's "threads confined" check. If it keeps printing
   `LowState is not available`, it isn't receiving robot state.
2. **Robot PC**: sensors only, then the full stack, with the robot still on the hoist:

   ```bash
   scripts/run_g1_real.sh --no-nav --net-if <iface>
   scripts/kill_ros_nodes.sh
   scripts/run_g1_real.sh --locomotion sonic --net-if <iface>
   ```

   On the robot PC, `ss -tnp | grep 5556` should show the Jetson connected.
3. **Progression**: hoisted idle, then hoisted short goals, then cancel a goal
   mid-motion to check the watchdog. Get a sign-off before feet down. Then short goals in
   open space, then mapping, then localization.

Profiles (`--sonic-profile`):

| Profile | vx fwd / rev | vy | wz |
|---|---|---|---|
| `slow_walk` (default) | 0.5 / 0.2 | 0.4 | 0.4 |
| `walk` | 0.8 / 0.3 | 0.4 | 0.5 |

Only use `walk` once `slow_walk` is solid. The collision monitor's static zones were
sized for the slower speed. `--sonic-arm-preset default|carry` holds a fixed upper-body
pose while walking. Validate it on the hoist first.

### Stopping

- The physical e-stop is always the primary stop.
- Cancel the goal or press `Ctrl-C` on the stack. The bridge idles the gait within
  0.3 s.
- To stop the controller itself, run `pkill -9 -f g1_deploy_onnx_ref` on the Jetson.
  The joints go compliant and the robot can sag.

### Troubleshooting

| Symptom | Fix |
|---|---|
| Robot falls after `Lost LowState data connection` | SONIC was started without `start_sonic_pinned.sh`. Restart it pinned. |
| `Init Done` but goals are ignored | The Jetson can't reach port 5556 on the robot PC. Check the firewall and `ss -tnp \| grep 5556`. |
| Robot won't turn | The bridge isn't receiving `/odom`, or `facing_lookahead_sec` is 0. |
| Walks about 15% slower than commanded | `speed_gain` is 1.0. The default is 1.18. |
| `crc_amd64.so: cannot open shared object file` | See unitree_sdk2py in [Robot PC setup](#robot-pc-setup). |
| `liblivox_lidar_sdk_shared.so` not found | Livox-SDK2 isn't installed, or you haven't run `ldconfig`. |
| `CUDA ... out of memory` on the Jetson | Run `sudo sh -c "sync; echo 3 > /proc/sys/vm/drop_caches"` and relaunch. |
